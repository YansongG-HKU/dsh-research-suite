# 领域研究闭环 · 0.4.0

> 后续版本：0.5.0 已补上条件适用性、监测指标判定、评审身份/COI 与 12 维闭环评分，见 [研究闭环-0.5.0](研究闭环-0.5.0.md)。本文保留 0.4.0 的设计与验收记录。

日期：2026-11-17  
范围：`dsh-research-suite` 0.4.0 的领域档案、九阶段闭环、审计/导出接线、面板与验收。  
结论口径：**“标准/清单对齐”不是认证、法律意见或临床合规结论**；机器能检查“记录是否到位”，不能替代领域评审人的判断。

---

## 1. 这次补上了什么

0.3.0 的九道闸门是“通用科研卫生”：问题、来源、预注册、真实运行、数字追溯、手稿引用、自动审查、发布声明。它挡不住下面这些问题：

- 金融回测在样本内调参，却把同一段样本叫“样本外”；
- 医学系统综述没有 PRISMA 识别/纳入计数，或纳入数大于识别数；
- AI 论文没有污染检查、切分说明、子群结果，却声称泛化；
- 工业试验没有测量系统分析（MSA/GR&R）、没有校准溯源，却报告“显著”；
- 四类研究都用同一套“两个评审”，没有量化/风险、临床/统计、ML/安全、工程/质量的角色分离；
- 发布即结束，没有监测计划、负责人、信号与回退路径。

0.4.0 增加一层**数据驱动的领域档案**：

| 项 | 数量/位置 |
| --- | --- |
| 领域 profile | 4：`finance` / `ai` / `medicine` / `industrial` |
| 领域字段 | 117（24 / 26 / 35 / 32） |
| 跨字段规则 | 2：金融样本内<样本外；医学 PRISMA 纳入≤识别 |
| 角色化评审 | 8 个角色，每个领域 2 个 |
| 监测信号 | 16 个默认信号（每领域 4 个） |
| 新工具 | `rsx_domain`（第 14 个） |
| 新面板路由 | `/api/domains`、`/api/domain/:id`、`/api/campaign/:id/domain`、`/api/campaign/:id/monitor` |
| 新导出 | `DOMAIN.md`；`REPORT.md` 增加 1.1 节与第 18 节；PROV/RO-Crate 带领域与监测属性 |

核心设计不是“给提示词加一段清单”，而是：

```text
state.domain = "finance"
  → domainChecks(state, stage) 生成 domain_finance_<field> 检查
  → gates.finish() 把它们并入该阶段 blocking
  → audit.checkDomain() 在审查中再次核对（只核对当前及之前阶段）
  → export 写 DOMAIN.md / REPORT.md / provenance.json / ro-crate-metadata.json
```

没有选择领域时，`domainChecks` 返回空数组，0.3.0 的行为完全保留；旧 campaign 没有 `domain` 字段也能继续跑。

## 2. 统一闭环：九阶段 + 领域挂点

| 阶段 | 通用闸门（0.3） | 领域挂点（0.4） | 典型阻断码 |
| --- | --- | --- | --- |
| scoping | 问题/边界/成功判据/档位/世界模型 | 对象、用途、授权、风险等级、伦理/注册、系统边界 | `domain_finance_mandate`、`domain_medicine_ethics_approval` |
| survey | ≥8 来源、≥2 一手、≥1 2023+、正文捕获、证伪检索、覆盖域 | 数据源/PIT、检索式、数据库、先验证据、测量计划 | `domain_ai_contamination_check`、`domain_industrial_msa` |
| hypothesis | 证伪条件、终止条件、预测、指标、≥2 支持、查新 | 领域假设通常复用通用项；领域字段可在 design 前补 | 通用 `hypothesis_*` |
| design | 预注册、负对照、环境锁 | 样本内/外、样本量/把握度、切分、成本模型、DOE/因子/重复 | `domain_finance_oos_after_in_sample`、`domain_medicine_sample_size` |
| execute | 真实运行、种子、指标、负对照 | 引擎/快照、数据锁定、设备状态、原始数据、校准记录 | `domain_industrial_calibration_record` |
| analyze | 数字 trace、数值一致、不确定性、断言状态 | 风险指标、效应量/CI、多重性、子群、不确定度、确认运行 | `domain_ai_subgroup`、`domain_industrial_confirmation_run` |
| write | 手稿、`{{N}}`、`[[src]]`、无游离数字、图溯源 | 报告清单、模型卡/数据卡、清单完成度、试验报告、安全案例 | `domain_medicine_checklist` |
| review | 2 份评审、≥1 红队、无 reject、无未解决 blocking、审计新鲜且验签 | 领域角色各 1 条、领域字段复核、领域审计 findings | `domain_ai_review_ml`、`domain_finance_review_risk` |
| release | 上游全过、AI 声明+水印+人工、dual-use、预算、链/状态 | 监测计划/负责人/频率/信号；领域发布字段 | `domain_finance_monitoring`、`domain_industrial_traceability` |

闭环不是“release 就结束”：

1. release 记录 `releasedAt`，监测进入 `planned/active`；
2. `rsx_campaign action:"monitor"` 更新 `status/plan/owner/cadence/signals/notes/reviewedAt`，每次写事件 `monitoring.updated`；
3. 监测信号触发时，用 `rsx_gate action:"back" stage:"analyze"`（或 design）回退，修正后重新审计、重新推进；
4. `gates`/`events` 保留前进与回退历史，`REPORT.md` 第 18 节展示监测状态。

这条“回退—重审—再发布”路径是当前实现真正的闭环；但它仍是**人工触发的闭环**，不是自动监测系统（见第 8 节）。

## 3. 四个领域档案

### 3.1 金融量化与投研 `finance`

| 阶段 | 字段 |
| --- | --- |
| scoping | `mandate` 投资授权与决策场景、`universe` 资产池与交易场所、`sample_period` 样本期与时间口径、`success_metric` 主指标与阈值 |
| survey | `data_sources` 数据源与 PIT、`survivorship_policy` 幸存者偏差/退市、`benchmark` 基准与无风险利率、`prior_evidence` 先验证据/已知异象 |
| design | `in_sample_end`、`oos_start`、`cost_model` 成本与容量、`multiple_testing` 多重检验/过拟合、`execution_assumptions` 成交与公司行动 |
| execute | `engine` 引擎/版本、`data_snapshot` 冻结快照、`portfolio_construction` 组合构建/再平衡 |
| analyze | `risk_metrics`、`out_of_sample_result`、`sensitivity`、`limitations` |
| write | `disclaimer`（必须含“不构成投资建议/not investment advice”）、`data_availability` |
| release | `conflicts`、`regulatory_status` |

标准锚点：SEC Marketing Rule 206(4)-1（假设性/回测表现与利益冲突披露的结构参考）、GIPS 2020（组合业绩计算与呈现口径）、Deflated Sharpe Ratio（多重检验/选择偏差）、PBO（回测过拟合概率）。

规则：

```text
in_sample_end < oos_start
```

它挡的是“样本内结束日 ≥ 样本外开始日”这种时间穿越。注意：规则只验证日期顺序，不验证数据是否真的 point-in-time，也不验证交易成本是否可实现；这些仍由 `data_sources`、`cost_model`、`execution_assumptions` 的文本与评审人负责。

角色：`quant`（量化/回测审查）+ `risk`（风险/合规审查）。  
监测：回撤、夏普衰减、换手、成本滑点；发布后应预先写明降仓/停用阈值。

**这个档案没有做什么**：没有接行情/财报供应商，没有自动计算 Deflated Sharpe/PBO，没有校验 GIPS composite 的资产加权口径，也没有判断策略是否构成投资建议。它只把“必须被记录和评审的协议点”变成可检查字段。

### 3.2 人工智能与机器学习 `ai`

| 阶段 | 字段 |
| --- | --- |
| scoping | `intended_use`、`out_of_scope`、`risk_tier`（low/limited/high）、`human_oversight` |
| survey | `baselines`、`benchmarks`、`data_provenance`、`contamination_check` |
| design | `data_splits`、`evaluation_protocol`、`seeds`、`compute_budget` |
| execute | `environment`、`hardware`、`inference_params` |
| analyze | `uncertainty`、`ablation`、`subgroup`、`calibration` |
| write | `limitations`、`model_card`、`data_card`、`license` |
| release | `safety_eval`、`model_access`、`incident_policy` |

标准锚点：NIST AI RMF 1.0（Govern/Map/Measure/Manage）、NIST AI 600-1（生成式 AI 风险）、ISO/IEC 42001:2023（AIMS 结构）、EU AI Act（高风险 AI 的数据治理/记录/人类监督/准确性）、NeurIPS Paper Checklist、Model Cards。

角色：`ml`（机器学习审查）+ `safety`（安全/伦理审查）。  
监测：accuracy drift、data drift、safety incident、eval regression；应写明回滚/停用条件。

**这个档案没有做什么**：没有自动跑污染检测、没有自动生成 model card、没有判定 EU AI Act 风险等级（`risk_tier` 是组织口径，不是法律结论）、没有做公平性统计检验。`subgroup`/`calibration` 是要求记录切片与校准证据，不是代替分析。

### 3.3 医学与临床研究 `medicine`

| 阶段 | 字段 |
| --- | --- |
| scoping | `population`、`intervention`、`comparator`、`outcomes`、`study_design`（9 类）、`registration_id`、`ethics_approval` |
| survey | `search_strategy`、`databases`、`screening`、`prisma_identified`、`prisma_included`、`risk_of_bias_tool` |
| design | `sample_size`、`randomization`、`blinding`、`analysis_set`（ITT/PP/safety/other）、`missing_data` |
| execute | `data_lock`、`protocol_deviations`、`adverse_events` |
| analyze | `effect_measure`（RR/OR/HR/MD/SMD）、`confidence_interval`、`multiplicity`、`risk_of_bias`、`certainty`（GRADE）、`sensitivity` |
| write | `reporting_guideline`、`checklist`、`funding`、`conflicts`、`data_sharing` |
| release | `safety_reporting`、`registration_update`、`ethics_statement` |

标准锚点：PRISMA 2020（系统综述）、CONSORT 2025（随机试验）、STROBE（观察性研究）、RoB 2（随机试验偏倚）、GRADE（证据确定性）、ICH E6(R3) GCP、TRIPOD+AI（预测模型）、CONSORT-AI（AI 干预试验扩展）。

规则：

```text
prisma_included <= prisma_identified
```

角色：`clinical`（临床审查）+ `statistics`（统计审查）。  
监测：adverse events、protocol deviations、data quality、safety signal；写明安全性报告与方案修订触发条件。

**这个档案没有做什么**：没有生成 PRISMA 流程图、没有逐项映射 27 条清单、没有计算样本量/把握度、没有做 RoB 2 域判断或 GRADE 降级、没有判断研究设计是否真的符合注册方案。`N/A — 理由` 可处理“某设计确实不适用某字段”，但不能替代方法学评审。

### 3.4 工业与工程研究 `industrial`

| 阶段 | 字段 |
| --- | --- |
| scoping | `system_boundary`、`operating_context`、`requirements`、`hazards`、`standards` |
| survey | `prior_art`、`measurement_plan`、`msa`、`calibration` |
| design | `design_type`（DOE/全因子/部分因子/响应面/验收/可靠性/other）、`factors`、`levels`、`replicates`、`randomization`、`acceptance_criteria`、`safety_review` |
| execute | `environment`、`raw_data`、`deviations`、`calibration_record` |
| analyze | `effect_estimates`、`assumptions`、`uncertainty`、`confirmation_run`、`capability` |
| write | `reporting_standard`（ISO-17025/IATF-16949/ISO-9001/IEC-61508/ISO-13849/other）、`test_report`、`limitations`、`safety_case` |
| release | `traceability`、`quality_record`、`safety_signoff` |

标准锚点：ISO/IEC 17025:2017（实验室能力/结果有效性）、IATF 16949:2016（汽车 QMS，MSA/SPC 核心工具）、AIAG MSA（GR&R/偏倚/线性/稳定性）、ISO 13849-1:2023（机械安全 PL）、IEC 61508（功能安全 SIL）、ISO 9001:2015（QMS）。

角色：`engineering`（工程审查）+ `quality`（质量/安全审查）。  
监测：SPC 告警、校准到期、缺陷率、安全事件；写明停线、召回与再验证触发条件。

**这个档案没有做什么**：没有做 GR&R 计算、没有生成控制图/过程能力指数、没有做 DOE 功效分析、没有分配 PL/SIL、没有替代 ISO/IEC 17025 认可或安全签核。

## 4. 跨领域控制模式

| 控制模式 | 在套件中的实现 | 机器能检查 | 机器不能检查 |
| --- | --- | --- | --- |
| 先定协议再跑 | design 预注册 + 领域 design 字段 | 字段存在、负对照、种子、环境锁 | 协议是否科学合理 |
| 数据时点 | 金融 PIT/样本外日期；工业校准有效期；医学数据锁定 | 文本记录、日期顺序 | 数据供应商是否真的 PIT |
| 偏差控制 | 医学 RoB/盲法/分配隐藏；AI 污染/切分；金融幸存者偏差/多重检验 | 字段与规则 | 实际执行是否到位 |
| 不确定性 | analyze 要求 ≥1 个不确定性；领域 CI/校准/测量不确定度 | 存在性与数字一致 | 区间方法是否正确 |
| 角色分离 | 每领域 2 个 role review | 是否有对应角色记录 | 评审人是否独立/有资质 |
| 可复现 | 预注册 seed/envLock、run 命令/退出码/stdout 工件 | 可追溯链 | 环境能否真的重建 |
| 报告清单 | 领域 standards + reportSections + checklist 字段 | 是否登记 | 清单是否逐项正确 |
| 发布后监测 | monitoring plan/owner/cadence/signals + report 第 18 节 | 计划是否完整 | 信号是否被真正监测 |
| 审计不可否认 | HMAC 签名 + subjectHash + stateHash | 篡改/过期 | 本地密钥拥有者 |
| 溯源导出 | PROV-JSON + RO-Crate + DOMAIN.md | 关系可解析 | 语义是否被外部工具完全接受 |

这些模式来自不同共同体，但落点一致：**把“结论之前必须存在的记录”变成状态机的一部分**。这是“集百家之长”的实际含义，不是把标准名字贴到提示词上。

## 6. 状态、审计与导出

### 6.1 状态形状

```jsonc
{
  "domain": "medicine",
  "domainData": {
    "population": "…",
    "prisma_identified": 120,
    "prisma_included": 18,
    "registration_id": "N/A — 本研究为系统综述，无试验注册"
  },
  "monitoring": {
    "status": "active",
    "plan": "每月复核不良事件与方案偏离，触发阈值即回退 analyze。",
    "owner": "临床负责人 / 统计负责人",
    "cadence": "monthly",
    "signals": ["adverse_events", "protocol_deviations"],
    "notes": "",
    "reviewedAt": "2026-11-17",
    "updatedAt": "2026-11-17T12:00:00.000Z"
  }
}
```

旧状态缺这三个字段时按 `null/{}/none` 处理，不迁移、不报错。

### 6.2 审计语义

- `auditSubject` 包含 `domain` 与 `domainData`：改领域字段会让上次审计 `fresh:false`。
- `checkDomain(state, findings)` 只检查**当前阶段及之前**的领域字段/规则/角色/监测，避免 release 字段在 review 阶段提前挡路。
- review 阶段缺角色会生成 `domain_<id>_review_<role>` blocking。因此领域 campaign 的正确顺序是：先加两条角色化 review，再运行 `rsx_review action:"audit"`；如果先 audit 再加 review，审计会过期。
- release 阶段会检查 monitoring；先 `rsx_campaign action:"monitor"` 写计划，再审计/推进。监测更新本身不进入 `auditSubject`，所以不会让审计无故过期；领域字段会。

### 6.3 导出

`DOMAIN.md` 只在该 campaign 有 `domain` 时生成，内容包括：

- 领域标题、摘要、字段完整度；
- 标准/框架表（标题、类型、用途、URL）；
- 报告结构建议；
- 字段登记表（阶段/字段/状态/内容或问题）；
- 未通过的领域检查；
- 审查角色与条数；
- 发布后监测表；
- “不构成认证/法律/临床合规”声明。

`REPORT.md` 的 1.1 节用 compact 版本（不重复全部字段表），第 18 节展示监测；`BUNDLE.zip` 条目包含 `DOMAIN.md`。`provenance.json` 的 `dsh:campaign` 实体增加 `dsh:domain`/`dsh:monitoringStatus`/`dsh:monitoringOwner`/`dsh:monitoringCadence`；RO-Crate 的 `#campaign` 增加 `keywords`。

## 7. 面板

侧边栏新增 **领域** 标签：

- 顶部显示当前 profile、摘要、完整度进度条；
- 下拉切换 profile（`general` 清除档案）；

## 8. 仍然缺什么（按优先级）

这部分是 0.4.0 之后真正需要补的，不是“已经做完”的装饰。

### P0：影响闭环可信度

1. **字段适用性仍是“全字段 required + N/A 理由”**  
   医学的 `registration_id` 对系统综述、工业的 `replicates` 对观察性数据、金融的日期字段对纯理论论文，都不该强制。当前用 `N/A — 原因` 豁免，等于把“判断”交给填写人。下一步应支持 `when` 条件（按 `study_design`/`design_type`/`risk_tier` 选择字段集），并在审计里检查“豁免是否被评审人确认”。
2. **监测没有数据面**  
   `monitor` 只记录计划/状态/信号，不接收监测指标，不会自动发现漂移、不良事件、SPC 告警。真正的闭环需要监测记录（时间、值、阈值、动作）与自动回退触发。当前只能人工 `gate back`。
3. **角色没有身份与独立性**  
   `role` 是字符串，不校验评审人是否独立、是否有资质、是否与作者重叠。HMAC 只证明“本机记录未被改”，不证明“这个人有资格”。需要 reviewer registry/COI 声明/外部签名。
4. **标准版本与适用性没有引擎**  
   profile 里写的是标准名与 URL，不判断“这项研究是否适用 EU AI Act 高风险”“这个试验该用 CONSORT 还是 STROBE”。需要按设计/风险分流的 applicability matrix，而不是让用户自选。
5. **审计不判断方法正确性**  
   它检查数字能追到运行、引文能追到正文，但不检查统计模型、样本量计算、GR&R 公式、Deflated Sharpe 公式是否正确。这是刻意的边界，不能把“审计通过”当成“方法正确”。

### P1：可用性与互操作

6. **条件字段/阶段跳过**：例如系统综述没有 execute 的原始数据锁定，纯理论金融研究没有样本外；需要显式的 `not_applicable` 结构化字段与审计确认。
7. **清单逐项映射**：PRISMA 27 条、CONSORT 2025、TRIPOD+AI、NeurIPS checklist 目前只有汇总字段；缺 item-level 的“条目→页码/位置”表。
8. **领域计算器**：样本量/把握度、GR&R、Cpk、Deflated Sharpe/PBO、SIL/PL 分配、DOE 功效；当前只要求记录，不计算。
9. **外部时间戳/透明日志**：HMAC 是本机密钥；跨机构验收需要 RFC 3161 时间戳或透明日志。
10. **多评审冲突处理**：两个角色都完成不等于结论一致；缺 `accept/minor/major/reject` 的分歧合并规则。
11. **领域模板仍偏少**：每个领域只有一个起步模板；缺少“系统综述”“诊断准确性”“ML 安全评估”“MSA/GR&R”“GIPS composite”等专用模板。
12. **跨领域组合**：AI+医学（TRIPOD+AI/CONSORT-AI）、AI+工业（机器学习+功能安全）需要组合 profile，而不是二选一。

### P2：生态与表达

13. **PRISMA 流程图/Consort 图**自动生成；当前只有计数与清单字段。
14. **Model Card/Data Card/Datasheet** 的结构化生成器；当前是文本字段。
15. **GIPS composite/业绩呈现**的报表模板；当前只有监管定位与声明字段。
16. **RO-Crate/PROV 的领域本体映射**：`dsh:domain` 是扩展属性，未映射到 CRediT/DCAT/Prov-O 的领域概念。
17. **多语言报告**：`DOMAIN.md` 目前中文为主，英文 profile 标题/摘要存在，但字段标签与报告仍是中文。
18. **监测 dashboard**：面板只有表单与报告表，没有时间序列/告警列表。

这些缺口不会因为“再加几个字段”自动消失；P0 的第 1、2、3 项需要状态机与外部系统接线，属于 0.5+ 的工作。

## 9. 新增一个领域的最小步骤

1. 在 `lib/domains.js` 定义 profile：

```js
const legal = {
  id: 'legal',
  title: label('法律实证研究', 'Empirical legal research'),
  summary: label('…', '…'),
  standards: [std('id', 'Title', 'reporting', 'https://…', '用途')],
  reportSections: ['…'],
  reviewRoles: [{ id: 'legal', label: label('法律审查', 'Legal review') }],
  monitoring: { required: true, planMin: 20, ownerMin: 2, cadenceMin: 2, signals: ['…'], guidance: '…' },
  fields: [
    text('research_design', 'scoping', '研究设计', 'Research design', { min: 12, help: '…' }),
  ],
  rules: [],
}
```

2. 加进 `DOMAINS` 与 `DOMAIN_IDS`（顺序决定面板顺序）。
3. 在 `assets/templates.json` 给相关模板加 `"domain": "legal"`，或新增模板。
4. 在 `test/unit/domains.test.mjs` 加：字段完整性、至少一个规则/豁免、角色与监测、导出 `DOMAIN.md`。
5. 跑 `npm test`、`npm run check`；不要改 `gates.js`/`audit.js` 的分支，它们通过 `domainChecks` 自动接入。

要求：字段必须映射到九阶段之一；规则必须是可判定的（日期顺序/数值比较/枚举），不要写“评审人认为合理”这种不可执行规则；标准 URL 要能打开；不要把认证/合规写成既成事实。

## 11. 边界声明

- 本套件做的是**研究记录与可复核性**，不是统计/临床/法律/安全认证。
- “标准对齐”只表示报告结构参考了该标准/清单，不表示研究符合标准，更不表示获得认证。
- `N/A — 理由` 是记录豁免，不是自动批准；评审人仍需确认豁免合理。
- 审计通过只表示“机器可复核的引用/数字/图/字段关系成立”，不表示结论正确。
- 监测计划存在不等于监测已执行；`status:"active"` 是记录状态，不是外部监控系统的心跳。
- 本机 HMAC 能挡本地状态篡改，不能挡拥有数据目录与密钥的攻击者；跨机构不可否认性需要外部信任根。
