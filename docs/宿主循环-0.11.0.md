# 宿主循环闸门（0.11.0）

## 目标

0.10 的 `rsx_campaign action:"next"` 是只读规划器：它知道下一步该调用什么，但不会阻止宿主在缺输入、缺人工批准或遇到未映射检查时继续执行。0.11 把“下一步”接成**每轮开始前的门**：

- 每次迭代前检查完整性、阶段预算、当前闸门、预注册时序和 `maxCycles`；
- 主推荐需要输入、需要人、或规划器没有具体配方时，**暂停并写入台账**；
- 人工补齐后，用显式 `resume:true` 恢复；阻断计划未变化时拒绝恢复，不写假记录；
- 推荐动作仍由宿主执行；循环闸门不调用模型、不执行工具、不自动批准、不豁免、不改预注册。

它解决的是“谁来踩刹车、刹车痕迹在哪里”，不是科学判断，也不是无人值守的科学家。

## 接口

```json
{
  "action": "loop",
  "campaign": "rs-…",
  "resume": false,
  "reason": "可选：恢复理由，最多 500 字"
}
```

返回的稳定字段：

```json
{
  "ok": true,
  "campaign": "rs-…",
  "status": "continue",
  "reason": "the primary action is deterministic and needs no human or placeholder input",
  "code": null,
  "stage": "survey",
  "iteration": 2,
  "maxCycles": 4,
  "plan": {},
  "primary": {},
  "checks": {
    "integrity": { "ok": true, "chainOk": true, "stateOk": true, "artifacts": 4, "problems": [] },
    "budget": { "ok": true, "tier": "M", "ratio": 0.0123, "tokensUsed": 492, "tokensLimit": 40000, "secondsUsed": 0, "secondsLimit": 1800, "overruns": [] },
    "prereg": { "ok": true, "detail": "…" },
    "gate": { "ok": false, "stage": "survey", "blocking": ["min_sources"], "passed": 2, "total": 9 },
    "cycles": { "ok": true, "used": 1, "max": 4 }
  },
  "stop": {},
  "loop": {
    "status": "idle",
    "pauseId": null,
    "pausedAt": null,
    "lastCheckAt": null,
    "lastStatus": null,
    "resumed": false,
    "resumeRejected": false,
    "stale": false
  },
  "pause": null
}
```

`status` 是本次调用的结果：`continue | pause | stop | ready`。`loop.status` 是持久状态：`idle | running | paused | ready | stopped`（`stopped` 只在显式写入时使用；当前停止不额外落盘）。`pause` 只在暂停时非空。

## 四种结果

| 结果 | 条件 | 写入 |
| --- | --- | --- |
| `continue` | 没有停止项；`primary` 不需要输入、不是人工检查点、不是未映射 | 不写 |
| `pause` | 没有停止项；`primary` 的 `needsInput`、`human` 或 `unmapped` 为真 | 首次写 `LP-xxxx` + `loop.paused`；重复检查不重复写 |
| `stop` | 完整性/预注册时序/预算/终止循环/`maxCycles` 触发；或没有主推荐 | 不写（完整性失败时绝不写） |
| `ready` | 发布闸门通过 | 不写 |

停止优先于暂停，顺序完全复用 0.10 的 `planNext`：

1. 完整性失败：`chainOk === false`、`stateOk === false` 或工件问题 → `stop{code:"integrity"}`；
2. 预注册锁定晚于首次运行 → `stop{code:"prereg_timing"}`；
3. 阶段预算超限 → `stop{code:"budget"}`；
4. 发布闸门通过 → `ready`；
5. 最新循环 `stop` / `escalate` → `stop{code:"cycle_stop"|"cycle_escalate"}`；
6. 循环数达到 `maxCycles` → `stop{code:"cycle_budget"}`。

因此暂停不会绕过预算、完整性或循环上限，也不会把“已发布但还有监控项”误判成继续。

## 暂停分类

- `needs_input`：主推荐带占位参数（例如 `<scope>`、`<analysis plan>`）；
- `human_checkpoint`：主推荐的 `human:true`（双重用途、人工批准、AI 声明等）；
- `unmapped_gate`：闸门或程序检查没有具体配方，规划器降级到 `rsx_gate action:"check"` / `rsx_program action:"list"`，并带 `unmapped:true`。

分类优先级是 `human` → `unmapped` → `needsInput`，所以一个人工检查点不会被误报成普通缺字段。

## 暂停记录

`state.loopPauses` 是行数组；首次暂停追加一行：

```json
{
  "id": "LP-0001",
  "at": "2026-11-18T…Z",
  "status": "open",
  "kind": "human_checkpoint",
  "reason": "primary action \"取得人工批准\" is a human checkpoint; …",
  "detail": "release requires a fresh human approval …",
  "stage": "release",
  "iteration": 5,
  "cycle": 4,
  "maxCycles": 6,
  "tool": "rsx_gate",
  "args": { "action": "approve", "approver": "<human name>" },
  "label": "取得人工批准",
  "needsInput": true,
  "human": true,
  "unmapped": false,
  "planHash": "…",
  "blocking": ["human_approval"],
  "gateOk": false,
  "integrityOk": true,
  "budgetRatio": 0.0123
}
```

同时写 `state.loop`：

```json
{ "status": "paused", "pauseId": "LP-0001", "pausedAt": "…", "lastCheckAt": "…", "lastStatus": "pause" }
```

事件链追加：

```json
{ "kind": "loop.paused", "payload": { "id": "LP-0001", "kind": "human_checkpoint", "stage": "release", "tool": "rsx_gate", "human": true, "needsInput": true, "unmapped": false, "planHash": "…", "cycle": 4, "maxCycles": 6 } }
```

`planHash` 是完整计划（含 `primary`、`steps`、`stop`）的规范 JSON SHA-256；它只用于判断“阻断是否还是同一个”，不是安全签名，也不替代审查对象哈希。

## 恢复

调用 `action:"loop" resume:true`：

1. 若当前仍返回 `pause`，无论阻断是否变化，都返回 `resumeRejected:true`，不写 `loop.resumed`，不修改 pause 行。这样 `resume:true` 不能被当成“跳过人工检查点”的暗门。
2. 若当前返回 `continue` / `ready` / `stop`，说明输入已经补齐或状态已经变化：把 open 行标为 `resumed`，写 `resumedAt` / `resumeReason`，把 `state.loop.status` 改为 `running`，追加 `loop.resumed`，然后返回新的结果。
3. 没有 open 行但 `state.loop.status === "paused"` 的旧状态，恢复时写一条 `loop.resumed`（`kind:"legacy_flag"`）后继续；这是迁移路径，不是正常路径。

恢复后如果命中 `stop`（例如补齐输入后预算已超），仍然返回 `stop`；恢复只清掉暂停，不改变停止规则。

## 与 `next` 的分工

| 入口 | 性质 | 用途 |
| --- | --- | --- |
| `action:"next"` | 纯函数、只读、确定性 | 查看计划、调试映射、面板“下一步”卡；不记录暂停 |
| `action:"loop"` | 有状态、只写暂停/恢复 | 宿主每轮前置闸门；暂停必须人工处理；恢复必须显式 |

`loop` 复用 `planNext` 的同一份计划，不复制排序或映射逻辑。`primary` 和 `plan.primary` 是同一个对象。

## 状态与兼容性

- 仍是 **16 个工具**；只扩展 `rsx_campaign` 的 `action` 枚举、`resume`/`reason` 参数和输出。
- 不修改 `SCHEMA_VERSION` / `PROGRAM_SCHEMA`，不修改九道闸门，不修改审查对象哈希的既有语义；`state.loop`/`state.loopPauses` 不进入审查对象字段（审查仍只看它已经覆盖的实体）。
- 旧 campaign 没有这两个字段：`normalizeLoopState` 返回 `idle`，首次暂停时才写；`stateHash` 在写入时按新状态重算。
- `loopPauses` 是独立台账，不占用 `cycles` 的 `maxCycles`：暂停不是一次研究行动，不能消耗循环预算，也不能替代 act→observe→decide 记录。

## 测试

`test/unit/loop-control.test.mjs` 8 个用例：

1. 安全主推荐返回 `continue`，状态与事件数不变；
2. 缺字段主推荐返回 `needs_input` 暂停；
3. 人工批准返回 `human_checkpoint`，未知检查返回 `unmapped_gate`；
4. 预算/完整性/循环预算三个停止优先于暂停；
5. 发布通过返回 `ready`；
6. 首次暂停写一条 `LP-0001`，重复检查幂等，未补输入时 `resume:true` 被拒绝且无写入，补齐后恢复成功并写 `loop.resumed`；
7. 真实流程到 release，人工批准暂停，审批数组保持为空；
8. 工具 schema 暴露 `loop`/`resume`，handler 返回暂停状态。

## 真实验收

2026-11-17 在本机 DSH（GUI `http://127.0.0.1:57091`）用真实宿主完成一次两周期循环，项目 `rs-a874c2ae`《0.11 宿主循环验收：真实题录与两次暂停》，档位 S，`maxCycles=5`：

1. `loop` 在定题阶段因 `scope` 缺失返回 `pause`，写 `LP-0001` 与 `loop.paused`；补齐 `scope` 后不传 `resume` 的检查仍返回 `pause`，`stale:true`，没有把“状态已变”当成自动恢复。
2. 传 `resume:true` 后写 `loop.resumed`，`LP-0001` 变为 `resumed`；主推荐 `world` 与 `rsx_gate advance` 都返回 `continue`，定题 5/5 通过，记录 `K-0001`。
3. survey 通过真实 `rsx_search` 查询 OpenAlex + Crossref：返回 8 + 8、合并 8 条，3,534 ms；登记 8 条真实题录与摘要（无伪造 DOI），记录 `Q-0001` 与实测反证检索 `Q-0003`（20 + 20、合并 10、0 条支持跳过检查点，3,453 ms）；survey 9/9 通过，记录 `K-0002`。
4. 推进到 hypothesis 后，`loop` 因 `rsx_claim` 仍是占位参数返回 `pause`，写 `LP-0002`；再次传 `resume:true` 得到 `resumeRejected:true`，审批数组保持为空，事件链仍是 24 条（拒绝恢复没有追加事件）。
5. 最终 `loop.status="paused"`、`pauseId="LP-0002"`、`K-0001/K-0002`、8 个内容寻址工件、`chainOk:true`、`artifactProblems:[]`；这是按设计停在输入检查点，不是伪造完成。

## 人工检查点真实验收（补充）

2026-11-18 在已发布项目 `rs-f7edf967` 上补做一次人工批准闭环。为让审批对象发生真实变化，先登记真实综述 `S-0011`（DOI `10.51584/ijrias.2026.11030104`）并在文稿局限段引用（930 字符），使旧审批 `P-0001` 失效。

第一次 `loop` 返回 `stop / cycle_stop`，因为该项目最后一条循环 `K-0001` 的决策是 `stop`；这验证的是停止优先，不是人工检查点。发布后证据修订需要新的批准，因此记录 `K-0002`（目标“为发布后的证据修订取得一次新的真实人工批准”，决策 `continue`），重新审计得到 `A-0003` / 对象哈希 `3a1cd91a…`。此时 `release` 为 11/12，唯一阻断 `human_approval`。

宿主再次调用 `loop`，返回 **`pause / human_checkpoint`**：`LP-0001` 写入并保持 open，`tool:"rsx_gate"`、`blocking:["human_approval"]`，`approvals` 没有增加。随后 YG 在会话中明确选择「批准（YG）」；只有在这次真人回答之后，才写入 `P-0002`（`approver:"YG"`、`subjectHash:"3a1cd91a…"`），`release` 变为 12/12，`loop resume:true` 写 `loop.resumed`（事件 76）并返回 `ready`。持久 `loop.status` 为 `running`、`lastStatus` 为 `ready`（恢复后不把一次性结果写成持久 ready）。

这说明三点：暂停记录不会代签；审批绑定审查对象哈希，证据改动会令旧批准失效；终止循环不会自动转成人工暂停，发布后修订必须显式记录新的修订循环或由人直接审批。证据在 `_artifacts/real-0.11-human/acceptance-human.json`，摘要并入 `_artifacts/real-0.11/acceptance-0.11.json`；面板实拍 `_artifacts/real-0.11-human/panel-human-1440.png` 显示 `rs-f7edf967` 已发布、全部闸门通过、事件链完整。

## 边界

- 不执行推荐：不调用模型，不跑命令，不写证据，不自动填占位符。
- 不自动批准：`human:true` 只能由人完成；`resume:true` 不会生成 approval，也不会改 approval 的 `subjectHash`。
- 不自动豁免：不调用 `rsx_gate action:"waive"`；暂停行不是 waiver。
- 不静默猜测：未映射检查返回 `unmapped:true` 并暂停；人工必须看 `rsx_gate action:"check"` 的具体 detail。
- 没有通知、超时、调度器、跨项目仲裁或自动重试；暂停后由宿主/人决定下一步。
- 暂停行记录的是“被阻断的计划”，不是已经发生的行动；真正的行动仍以 `cycles`、`runs` 和实体台账为准。
