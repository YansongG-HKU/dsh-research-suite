# 1.0.0：迁移、备份与恢复

这篇文档只讲操作，不重复设计理由。设计和契约边界见[发布契约](1.0.0-发布契约.md)。

## 1. 兼容矩阵

| 原 schema | 1.0 读取 | 自动改状态 | 迁移后新增的强制面 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | 是 | 否 | schema 2 来源/风险偏倚、schema 3 检索/敏感性、schema 4 研究程序、schema 5 治理 | 先 dry-run，确认旧项目能否补齐；不要批量迁移 |
| 2 | 是 | 否 | schema 3 检索/敏感性、schema 4 研究程序、schema 5 治理 | 已发布项目保留 schema 2，必要时另建新项目 |
| 3 | 是 | 否 | schema 4 研究程序、schema 5 治理 | 先看 `program.missing`，再决定是否迁移 |
| 4 | 是 | 否 | schema 5 治理 | 最常见路径；dry-run 后补治理字段即可 |
| 5 | 是 | 不适用 | 无 | 已是当前契约 |

关键点：**升级插件不会自动迁移**。schema 1–4 项目的旧检查继续按旧契约 advisory 或 blocking，不会因为安装了 1.0 就突然被阻断；只有调用 `migrate` 才把项目切换到 schema 5，并同时承担 1.0 的全部强制检查。

## 2. 迁移前检查

在 DSH 会话里调用只读体检（不会创建密钥、不会修复）：

```json
{ "tool": "rsx_campaign", "arguments": { "action": "doctor" } }
```

确认目标项目：

- `chainOk: true`
- `stateOk: true`
- `artifactProblems: []`
- `lock` 不是活跃或陈旧写锁
- 最新审计不是 `stale_audit`（迁移本身不会让审计过期；但迁移前的审计缺口应被看见）

然后 dry-run：

```json
{
  "tool": "rsx_campaign",
  "arguments": {
    "action": "migrate",
    "campaign": "rs-xxxxxxxx",
    "dryRun": true,
    "stewardship": {
      "license": "CC-BY-4.0",
      "dataAvailability": "数据与导出包随论文附录提供。",
      "codeAvailability": "代码在仓库内，Node 22 可重跑。",
      "competingInterests": "无。",
      "ethics": "不涉及人类受试者。",
      "contributors": [{ "name": "YG", "roles": ["conceptualization", "supervision"] }]
    }
  }
}
```

dry-run 返回：

- `from` / `to`
- `missing`：治理字段还缺什么
- `program`（原 schema < 4 时）：研究程序还缺什么
- 不写备份、不改 `state.json`

## 3. 执行迁移

去掉 `dryRun`，重复同一个调用。成功时：

1. 验证事件链、state 哈希和全部工件；
2. 在 `campaigns/<id>/backups/` 写 `backup-*.zip`；
3. 将 `state.schema` 设为 5，合并治理字段；
4. 写入 `campaign.migrated` 事件；
5. 保存新 `stateHash`，更新 `index.json`；
6. 返回 `backup.name`、`backup.sha256`、`migrate` 记录和当前 release 闸门。

备份 ZIP 包含：

```text
manifest.json   # 项目 id、schema、seq、lastHash、创建时间、原因、工件计数
state.json      # 迁移前的完整物化状态
events.jsonl    # 迁移前的事件链
```

工件不复制：它们是内容寻址的，迁移不修改内容；完整导出仍用 `rsx_write action:"export"`。

每个项目最多保留 20 份备份，超出后删除最旧的。备份只在本地数据目录，不导出、不进入 `BUNDLE.zip`。

## 4. 回滚

1.0 **没有自动回滚**。自动回滚会在链上再写一次状态变更，容易把“恢复”变成第二次不可审计的变更；因此回滚是显式的文件操作。

```text
1. 停止对该项目的写入（关闭正在写它的会话；确认 doctor 没有 active_lock）。
2. 解压 backups/<backup>.zip 到临时目录。
3. 备份当前 campaigns/<id>/state.json 与 events.jsonl（可选但建议）。
4. 把 ZIP 内的 state.json 与 events.jsonl 覆盖回 campaigns/<id>/。
5. 重启/重载插件，调用 doctor。
6. 若 index.json 因覆盖而落后，调用 action:"reindex"。
7. 确认 chainOk、stateOk、artifactProblems 为空；需要时重新审计。
```

注意：

- 必须同时恢复 `state.json` 和 `events.jsonl`。只恢复 state 会让链尾与事件数不一致，`doctor` 会报 `chain_broken`。
- 恢复后 `stateHash` 来自旧状态，仍应通过校验；如果失败，说明解压或覆盖不完整。
- 恢复会把项目契约退回迁移前 schema；已写入的 `campaign.migrated` 事件随事件文件回退而消失，这是预期的。
- 如果备份文件损坏，使用 `sha256` 与 ZIP 的 CRC 检查；没有可用备份时，用上一次完整导出包中的 `campaign.json` + `ledger.jsonl` 作为最后手段，并人工核对链尾。

## 5. 索引、锁与审计

**索引**：`index.json` 是缓存，campaign 目录是事实源。`doctor` 发现 `missing/orphan/duplicated/currentMissing` 时，`reindex` 只从目录重建索引，不修改 `state.json`。索引损坏不会丢数据。

**写锁**：`.write.lock` 正常写入时短暂存在。超过 `lockStaleMs`（30 秒）显示为 `stale_lock` warning；`doctor` 不删除锁。确认没有进程在写后，删除该文件或等待下一次写入回收；不要在写入过程中手动删锁。

**审计**：迁移不改治理字段之外的审计对象；治理字段本身不在审计对象哈希中。若迁移后改动了来源、证据、数字或手稿，旧审计会变成 `stale_audit`，需要重新运行 `rsx_review action:"audit"`。发布前仍需当前对象哈希上的人工批准。

**签名密钥**：`signing-key.json` 在数据目录根部，首次审计时创建。`doctor` 只读取已有密钥，不会为了体检而创建密钥。密钥损坏时审计验签 fail-closed；不要删除密钥来“修复”，那会让所有旧审计失效。

## 6. 常见失败

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `integrity_blocked` | 链、state 哈希或工件校验失败 | 先修复/恢复；不要绕过迁移 |
| `stale_state` | 另一个进程已推进项目 | 重新读取项目后重试 |
| `unsupported_schema` | 项目 schema 比当前插件新 | 升级插件；不要降级写 |
| `doctor` 报 `schema_outdated` | schema < 5 | 这是 info，不是错误；按需 dry-run |
| 迁移后 release 仍阻断 | 治理字段或旧契约检查未满足 | 看 `gate.blocking`，逐项补齐 |
| `BUNDLE.zip` 超限 | 报告+事件+工件超过 64 MB | 用独立导出目录；ZIP 不是唯一交付 |

## 7. 操作者清单

- [ ] 升级前导出一次当前项目包，保存到仓库外。
- [ ] `doctor` 全绿或有可解释的 warning。
- [ ] `migrate dryRun:true` 看 `missing` 与 `program`。
- [ ] 补齐治理字段；schema < 4 的项目同时补研究程序。
- [ ] 执行 `migrate`，记录返回的 `backup.name` 与 `backup.sha256`。
- [ ] 迁移后 `doctor` 确认 `chainOk`、`stateOk`、`index.ok`。
- [ ] 重新审计（如项目内容有改动），重新取得人工批准。
- [ ] 通过 release 闸门后再导出 `BUNDLE.zip`，核对 `MANIFEST.json`。
