# 可视化迭代飞轮（0.12.0）

0.11 的宿主循环已经有了暂停、恢复和下一步计划，但总览页仍是一条线性阶段条。它能回答“现在在哪个阶段”，回答不了“这个阶段被哪道闸门卡住、下一步调用什么、是否在等人工、这一圈和上一圈有什么不同”。0.12 把总览改成飞轮工作台：环形九阶段、右侧状态栏、底部五动作区和下方真实轮次轨迹，四者都只读当前项目的台账。

## 布局

```
活动项目条
项目标题 / 问题 / tier / 事件链 / id / 时间
┌───────────────────────────────┬─────────────────────────────────────┐
│ 九阶段 SVG 环（340×340）      │ 当前阶段 + 闸门 / 开放暂停          │
│ 中心：第 N 圈 · 阶段 · done/9 │ 四个真实指标                        │
│                               │ 下一步动作（可复制调用）            │
└───────────────────────────────┴─────────────────────────────────────┘
研究动作：导出 / 台账 / 审查 / 报告 / 归档
迭代轨迹（最近 4 圈）        闸门检查
项目事实                     研究闭环
```

右侧栏顺序固定为 **当前阶段 → 当前闸门 → 开放暂停 → 指标 → 下一步**；五个动作在飞轮卡片底部单独成行，不再散落在下一步卡和页脚。右栏不是单独的 fixed 浮层，而是飞轮卡片内的第二列；页面滚动时随卡片移动，避免遮住台账内容。动作行是文档流的一部分，滚动到卡片底部即可看到。

## 数据映射

| UI | 来源 | 规则 |
| --- | --- | --- |
| 九个节点 | `STAGES` + `state.stage` | 当前阶段之前的节点为 `done`；当前阶段无闸门或闸门通过为 `done`，阻断为 `blocked`，否则 `current`；后续为 `pending` |
| 当前节点阻断 | 详情接口的 `gate` | 当前阶段尚未写入 `state.gates` 时，用 `gate.stage === state.stage` 的实时结果补位；当前闸门失败直接标红，不伪装成普通“进行中” |
| 圆环进度 | `done / 9` | 只数已完成阶段，不按时间、事件数或预算估算 |
| 中心圈数 | `state.cycles.length` | 有轮次显示 `第 N 圈`，没有轮次显示 `预备` |
| 闸门指标 | `gate.passed / gate.total` | 当前闸门检查的真实通过数，不汇总历史最大值 |
| 证据 / 来源 / 事件 | `state.evidence.length`、`state.sources.length`、`state.seq` | 只读数组长度与事件序号 |
| 暂停卡 | `state.loop` / `state.loopPauses` | 优先取最后一条 `status:"open"` 的记录；区分 `human_checkpoint`、`needs_input`、`unmapped_gate`；没有开放记录但 loop 为 paused 时给出缺失提示 |
| 下一步 | 详情接口 `next` | `next.stop.ready` → 可交付；`stop.blocked` → 阻断原因；否则显示 `next.primary` 的工具、参数和“继续研究/复制调用”。导出按钮不再放在这里 |
| 导出动作 | 当前发布节点 + `state.loop/loopPauses` + `state.archived` + `busy` | 仅当 release 节点 `gateOk === true`、没有 open pause、未归档且不忙时启用；否则 `disabled` |
| 台账 / 审查动作 | 无额外条件 | 只读，始终启用，包括暂停时；用于先检查再恢复 |
| 报告动作 | `stage` 的序号 | 从 `write` 阶段起启用；之前禁用并提示“写作阶段后可查看报告” |
| 归档动作 | 同导出 + `window.confirm` | 与导出一致的发布/暂停/归档/忙门；点击后仍须父级确认，确认框未改 |
| 禁用原因 | `flywheelActionAvailability` | 优先级：暂停 > 已归档 > 发布闸门未过 > 处理中；`title` 和 `aria-disabled` 同时暴露原因，禁用时不挂 `onClick` |
| 轮次轨迹 | `state.cycles` 最后 4 条 | 显示 `K-xxxx`、决策、时间、运行、目标、观察；决策 `continue` 绿、`stop/escalate` 红，其余黄；没有轮次显示空状态 |

没有新增独立评分。研究闭环分数仍来自既有 `loopEvaluation`，飞轮只做导航，不把视觉进度写回状态。

## 动作区：改动前后对比

改动前的 0.12.0 首版把动作分散在三处：下一步卡里只有就绪时的 `导出研究包` 和 `查看台账`，页脚有 `查看审查 / 查看报告 / 归档`。这些入口没有统一的可用性模型：暂停、发布阻断或归档后，页脚三个入口仍然可点；报告在 `write` 之前也能打开；导出在未就绪时直接消失，没有解释。下表是同一套真实状态在改动前后的行为对照。

| 动作 | 改动前 | 改动后 | 本次实测 |
| --- | --- | --- | --- |
| 导出 | 只在 `next.stop.ready` 时出现；暂停/阻断时消失，无原因；不看归档与 busy | 发布闸门通过 + 无 open pause + 未归档 + 不 busy 才启用；否则原生禁用并给出原因 | 完成态启用，点击写出 `BUNDLE.zip` 并 toast；暂停态禁用 `先处理当前暂停` |
| 台账 | 下一步卡中的链接，始终可点 | 统一动作区，始终可点 | 暂停态仍启用，点击进入台账 |
| 审查 | 页脚链接，始终可点 | 统一动作区，始终可点（只读） | 暂停态与完成态均启用；完成态点击进入审查 |
| 报告 | 页脚链接，始终可点 | 从 `write` 阶段起启用，之前禁用并提示 | 完成态点击进入报告；暂停在 `hypothesis` 时禁用 `写作阶段后可查看报告` |
| 归档 | 页脚链接，始终可点，只有 confirm | 与导出相同的发布/暂停/归档/忙门，confirm 保留 | 完成态启用；暂停态禁用 `先处理当前暂停` |

状态矩阵（由 `flywheelActionAvailability` 和渲染测试共同覆盖）：

| 状态 | 导出 | 台账 | 审查 | 报告 | 归档 |
| --- | --- | --- | --- | --- | --- |
| 发布完成，release `gateOk=true` | 可用 | 可用 | 可用 | 可用 | 可用 |
| 暂停（`hypothesis`，`LP-0002` open） | 禁用：暂停 | 可用 | 可用 | 禁用：写作前 | 禁用：暂停 |
| `hypothesis`，无暂停 | 禁用：发布闸门 | 可用 | 可用 | 禁用：写作前 | 禁用：发布闸门 |
| release 阻断 `11/12` | 禁用：发布闸门 | 可用 | 可用 | 可用 | 禁用：发布闸门 |
| 已归档 | 禁用：已归档 | 可用 | 可用 | 可用 | 禁用：已归档 |
| 写入中（`busy`） | 禁用：处理中 | 可用 | 可用 | 可用 | 禁用：处理中 |

六个状态、五个动作的断言在 `test/unit/client.test.mjs` 中；除纯函数外，测试还会用 React 元素桩渲染 `Flywheel` 的元素树，逐个读取 `data-action`、`disabled`、`title` 和 `onClick`，避免“规则写对了但按钮没接上”。同一套状态矩阵另由 `test/unit/panel.test.mjs` 通过真实 loopback HTTP 对 `/api/export/:id` 和归档 action 断言：被拒绝时统一返回 HTTP 409、`code:"action_blocked"`、`detail.reason` 与客户端一致的 `paused / archived / release / busy`，而不是静默成功。

## 兼容与回退

## 风险与边界

- **状态栏是卡片内的右列，不是 viewport sticky**。如果以后要求滚动时始终悬浮，需要另做 sticky 容器，并处理窄屏遮挡。
- **轨迹只显示最近 4 圈**。更早的轮次仍在台账/事件链里；这是密度取舍，不是数据删除。
- **窄屏没有伪造 390px 设备帧**。DSH 桌面窗口有最小宽度（实测外宽 668px，内容约 600px）；另用 520px 内容视口验证了 ≤700px 断点。若需要严格 390px 截图，应使用 DSH web 端或无头浏览器，而不是压缩桌面窗口。
- **无循环的项目显示“预备”**，即使闸门已推进；这是如实表达“没有轮次记录”，不推断轮次。
- **当前闸门实时补位**依赖详情接口返回 `gate.stage`；若未来接口改名，需要同步更新 `flywheelModel` 的匹配条件。
- **动作门已有客户端与服务端两层**。`flywheelActionAvailability` 仍负责按钮可用性；`/api/export/:id` 与归档 action 在路由层调用 `service.actionGate`，服务层 `archive()` 也复核，因此直接请求面板 API 或走 `rsx_campaign action:"archive"` 都会被同一策略拦下。残余路径是 `rsx_write action:"export"` 仍直接调用 `service.write`，不经 HTTP 动作门；若要让工具导出也强制发布闸门，需单独处理，因为既有测试里有多处故意导出未发布项目的断言。
- **暂停时台账/审查故意保持可用**，因为恢复前先读证据是正常流程；如果以后要求“暂停即全锁”，需改 `flywheelActionAvailability` 并同步动作测试。
- **归档没有真实删除路径**：`store.archive` 只把 `archived` 置为 `true` 并写事件，数据保留；当前没有物理删除路由。验收中完成态点击归档、确认框出现后选择取消，暂停态只验证 409 与原因；服务端测试覆盖归档成功后的 `archived` 状态和后续导出被拒，但没有执行“确认归档→物理删除”，因为服务本身不提供物理删除。
